## 第一章 为什么需要向量数据库？

### 1.1 传统数据库的局限

传统关系型数据库（如 MySQL、PostgreSQL）和全文检索引擎（如 Elasticsearch）的核心检索逻辑是**关键词精准匹配**或规则匹配。这种方式存在两个根本缺陷：

- **无法识别语义**：“开心”和“高兴”在关键词匹配下可能完全无法关联，但语义上高度相似
- **无法处理非结构化数据**：图像、音频、视频等数据需要人工标注特征，无法端到端处理

### 1.2 向量数据库的核心价值

向量数据库的出现，从根本上解决了上述问题：

- **语义检索**：通过 Embedding 模型将文本、图像等数据转为高维向量，在向量空间中按距离衡量语义相似度
- **端到端处理**：直接存储和检索嵌入向量，无需人工特征工程，打通非结构化数据检索全链路

### 1.3 ANN 算法：高维空间的近似搜索

向量数据库的底层依赖**近似最近邻（ANN）算法**。这背后的核心挑战是“维度灾难”：

- 低维空间（2D/3D）中，KD-Tree 等树结构可以高效精确搜索
- 但在 768 维或更高维度中，任何树结构都会退化为几乎全量扫描
- ANN 算法的解决思路：放弃 100% 精确，用聚类、图、哈希等方式，在毫秒级内找到“足够近似”的结果

### 1.4 应用场景

除了最核心的 RAG（检索增强生成）场景外，向量数据库还广泛应用于：

- 推荐系统（用户/商品向量相似度匹配）
- 图像搜索（以图搜图、相似图片检测）
- 异常检测（金融交易、日志分析中的离群点发现）
- 多模态检索（文本搜图、图文互搜）
- 生物信息学（蛋白质结构、基因序列相似性分析）

## 第二章 Milvus 的核心优势

### 2.1 性能与架构

- **高性能**：高并发场景下依旧保持毫秒级低延迟，十亿级数据仍可稳定响应
- **存算分离**：云原生四层架构，各组件可独立弹性扩展，比传统数据库+向量插件的方案更具弹性
- **流批一体**：数据先写入消息队列（流），再异步持久化到对象存储（批），兼顾实时性和成本

### 2.2 部署与运维

- **部署灵活**：支持单机 Docker 快速上手学习，也支持 Kubernetes 集群投入生产
- **运维省心**：自带监控（Prometheus 指标暴露）与容错机制，支持滚动升级
- **开源免费**：Apache 2.0 协议，商用无版权顾虑

### 2.3 功能与生态

- **功能完备**：向量检索、标量过滤、混合搜索、全文检索、数据动态增删、多向量字段支持
- **生态兼容**：无缝对接 LangChain、LlamaIndex、Haystack 等主流 AI 框架
- **多语言 SDK**：Python、Java、Go、Node.js 等，满足不同技术栈需求

### 2.4 向量数据库 vs 传统数据库+向量插件

很多人问：为什么不直接在 PostgreSQL 上用 pgvector 插件？核心差异：

| 维度           | 专用向量数据库（Milvus）        | 传统数据库 + 向量插件                |
| :------------- | :------------------------------ | :----------------------------------- |
| **索引构建**   | 异步、增量、不阻塞写入          | 通常同步构建，写入吞吐受限           |
| **内存管理**   | 精细化 Segment 粒度加载/淘汰    | 依赖数据库通用 Buffer Pool           |
| **查询优化**   | 向量搜索 + 标量过滤真正融合执行 | 通常是两步：先过滤再搜，或先搜再过滤 |
| **扩展性**     | 存算分离，各组件独立弹性        | 整体扩缩，难以精细控制               |
| **性能天花板** | 十亿级数据仍可毫秒响应          | 千万级数据后性能急剧下降             |

## 第三章 Milvus 架构深度解析

Milvus 2.x 采用云原生存算分离的四层架构：

### 3.1 访问层（Access Layer）

- 由**无状态代理（Proxy）**组成，负责请求路由、负载均衡、身份验证与结果聚合
- 支持 gRPC 和 RESTful 两种通信协议
- 无状态设计使其可以随时重启，不影响数据完整性

### 3.2 协调层（Coordinator Layer）

集群的控制中心，包含四类协调器：

- **Root Coordinator**：管理元数据，处理 DDL 操作（创建/删除 Collection、Partition）
- **Query Coordinator**：管理查询节点的拓扑，分配查询负载
- **Data Coordinator**：管理数据节点的数据分配与持久化
- **Index Coordinator**：调度索引构建任务

### 3.3 工作节点层（Worker Node Layer）

三类节点，均可独立横向扩展：

- **Query Node**：执行历史数据检索，按需将 Sealed Segment 加载到内存
- **Data Node**：消费日志数据，生成 Segment 并持久化到对象存储
- **Index Node**：专门在后台异步构建向量索引，不阻塞读写

### 3.4 存储层（Storage Layer）

- **Meta Store**（etcd）：保存集群元数据、Schema、索引配置等
- **Object Storage**（MinIO/S3）：存放历史数据（Sealed Segment）与索引文件
- **Log Broker**（Pulsar/Kafka）：消息队列，保障流数据可靠性，支持多种主流实现

### 3.5 数据流转机制：流批一体

text

```
写入流程：
Client → Proxy → Log Broker → Data Node → Object Storage
                      ↓
                Query Node 订阅日志 → Growing Segment（内存，可实时查询）

索引构建：
Data Node 持久化 → Sealed Segment → Index Node 构建索引 → 索引文件写回 Object Storage
```



**Segment 是 Milvus 的最小调度单元：**

- **Growing Segment**：刚写入、未持久化的数据，查询时进行暴力搜索（无索引），保证实时可见
- **Sealed Segment**：已持久化的数据，触发索引构建后查询走索引，性能大幅提升

### 3.6 时间旅行与一致性

基于日志的时间戳，Milvus 支持**时间旅行（Time Travel）**，可查询过去某个时间点的数据快照。

四种一致性级别：

| 一致性级别     | 含义                         | 适用场景                                |
| :------------- | :--------------------------- | :-------------------------------------- |
| **Strong**     | 查询前等待所有数据同步完成   | 金融、订单等严格一致性场景              |
| **Session**    | 同一会话内保证看到自己的写入 | 用户操作后立即查看结果                  |
| **Bounded**    | 允许指定时间范围内的延迟     | 对延迟有明确容忍度的场景                |
| **Eventually** | 允许微小延迟，优先保证性能   | 常规搜索推荐场景（QPS 通常提升 30-50%） |

### 3.7 存算分离的工程价值

- **资源隔离**：查询是读密集型（CPU/内存），索引构建是计算密集型（CPU），可分别扩缩容
- **故障隔离**：Query Node 宕机不影响数据写入，Proxy 无状态可随时重启
- **成本优化**：夜间查询低谷期缩减 Query Node，索引构建期临时扩容 Index Node

## 第五章 数据库（Database）

在 Milvus 中，数据库是高于集合的一级逻辑单元。

### 5.1 核心作用

- **多租户管理**：不同业务线、不同客户的数据隔离
- **数据隔离**：各数据库的集合、索引、配额独立管理

### 5.2 操作与配置

- 安装后系统自带一个**默认数据库（default）**，不可删除
- 通过 SDK 或 API 可创建、查看、切换、删除自定义数据库
- 可配置属性：副本数量、集合上限、磁盘配额、读写权限、默认时区等
- **注意**：删除自定义数据库前必须先清空库内所有集合
- 所有数据库访问权限由 **RBAC 机制**统一管理
- 新建集合时，会直接继承所属数据库的默认配置

## 第六章 集合（Collection）

集合是 Milvus 的核心数据单元，等同于关系型数据库的数据表。

### 6.1 数据结构定义

每个集合通过 Schema 定义数据结构模板，包含：

- **主键字段**：每条数据的唯一标识（INT64 或 VARCHAR）
- **向量字段**：参与语义检索的向量数据，指定维度和数据类型
- **标量字段**：文本、数字、布尔值等附加属性，用于条件过滤

### 6.2 创建时的关键参数

| 参数                    | 说明                     | 建议                               |
| :---------------------- | :----------------------- | :--------------------------------- |
| **索引开关**            | 创建时开启则自动加载索引 | 生产环境建议开启，避免手动加载遗漏 |
| **分片数量**            | 数据分片数               | 行业建议每 2 亿条数据一个分片      |
| **一致性级别**          | 见第三章的四种模式       | 根据业务在一致性和性能间取舍       |
| **TTL（数据生命周期）** | 到期自动清除             | 适合日志、对话历史等时效数据       |
| **Partition Key**       | 自动分区键               | 按租户ID、时间等高频过滤字段设置   |

## 第七章 Schema 与字段设计

Schema 是集合的数据结构蓝图，约束所有数据的格式和数据类型。

### 7.1 字段分类

**向量字段：**

- 存放参与语义检索的向量数据（稠密向量、稀疏向量、二进制向量）
- 一个集合可同时定义**多个向量字段**（Milvus 2.4+），每个字段独立配置索引
- 稠密向量类型：`FLOAT_VECTOR`、`FLOAT16_VECTOR`、`BFLOAT16_VECTOR`

**标量字段：**

- 存储文本、数字、布尔值等附加属性
- 主要用途：数据筛选、条件过滤、结果展示
- 支持类型：INT64、FLOAT、DOUBLE、VARCHAR、BOOL、JSON、ARRAY

### 7.2 灵活 Schema 策略

- **必须定义主键**：每条数据的唯一标识
- **支持自动生成主键**：开启后系统自动赋值（INT64 类型，自增）
- **支持动态 Schema**：未提前定义的新增字段，自动收纳到 JSON 元数据字段中，适合字段不确定的场景

## 第八章 数据写入与删除

### 8.1 数据插入

支持两种方式：

- **单条录入**：适合实时性要求高的增量数据
- **批量导入**：适合大规模离线数据迁移

**性能建议：** 批量插入时每批控制在 1,000 - 10,000 条，数据库吞吐性能最优。数据提交后系统自动完成持久化保存。

### 8.2 更新插入（Upsert）

有数据就更新，没有数据就直接插入，特别适合业务增量更新的场景，避免维护“存在则更新、不存在则插入”的复杂逻辑。

### 8.3 数据删除

- **按主键精准删除**：指定主键值删除单条数据
- **按条件批量删除**：使用布尔表达式批量删除符合条件的数据

**重要注意事项：**

- Milvus 的删除属于**异步操作**
- 执行删除指令后，数据只是被标记为“已删除”，不会立刻释放磁盘空间
- 只有等待后台 **Compaction（数据压缩合并）** 完成后，对应的存储空间才会真正释放
- 查询时会自动过滤已标记删除的数据，对业务透明

## 第九章 索引

索引是加速查询而额外创建的数据结构。索引选型是在**查询速度、检索精度、资源消耗**三者之间寻找最优平衡。

### 9.1 索引分类

**标量索引：**

- 加速普通字段的条件过滤
- 支持：字典树、位图、排序、倒排等索引类型

**向量索引（三大类）：**

- **稠密向量索引**：如 HNSW、IVF_FLAT、DiskANN
- **二进制向量索引**：如 BIN_IVF_FLAT
- **稀疏向量索引**：如 SPARSE_INVERTED_INDEX

### 9.2 常用向量索引对比

| 索引类型     | 适用场景                      | 优点                           | 缺点                 |
| :----------- | :---------------------------- | :----------------------------- | :------------------- |
| **FLAT**     | 小数据量(<10万)，需要100%召回 | 精确搜索                       | 速度慢，内存大       |
| **IVF_FLAT** | 中等规模，高召回率            | 压缩搜索空间，速度快           | 内存占用仍较高       |
| **IVF_PQ**   | 大规模数据，内存受限          | 向量压缩，大幅节省内存         | 有精度损失           |
| **HNSW**     | 高吞吐、低延迟                | 综合查询性能最强               | 内存占用高           |
| **SCANN**    | 性能与精度兼顾                | 综合平衡性最好                 | 构建时间较长         |
| **DiskANN**  | 十亿级别超大集群              | 基于磁盘存储，大幅降低硬件成本 | 延迟略高于全内存方案 |

### 9.3 索引选型决策矩阵

| 场景         | 数据量    | QPS要求 | 召回率要求 | 推荐索引          | 关键参数                 |
| :----------- | :-------- | :------ | :--------- | :---------------- | :----------------------- |
| 原型验证     | <10万     | 低      | 100%       | FLAT              | 无                       |
| 实时搜索服务 | 百万-千万 | >1000   | >95%       | HNSW              | M=16, efConstruction=200 |
| 海量低成本   | 亿级+     | 中      | >90%       | DiskANN           | 内存预算控制             |
| 内存受限     | 千万级    | 中      | >85%       | IVF_PQ            | nlist=4096, m=8          |
| 多租户SaaS   | 十亿级    | 高      | >95%       | SCANN + Partition | 按租户ID分区             |

### 9.4 HNSW 内存估算公式

HNSW 是使用最广泛的索引，其内存消耗常被低估：

text

```
内存 ≈ 1.1 × (向量数 × 维度 × 4字节 + 向量数 × M × 2 × (4 + 8)字节)
```



示例：1000万条768维向量，M=16：

- 向量本身：10M × 768 × 4 = 30.7 GB
- 图结构：10M × 16 × 2 × 12 = 3.84 GB
- **总计约 34.5 GB**，需要预留 1.5 倍给查询时的临时内存

### 9.5 补充知识

- **自动索引（AutoIndex）**：系统根据数据量级和硬件配置自动匹配最优索引类型和参数，适合快速原型开发。但生产环境中手动调参通常可额外提升 20-30% 性能
- **异步构建**：创建索引是异步任务，全程不影响正常数据读写
- **相似度计算方式**：创建向量索引时必须选定，常用有余弦相似度（COSINE）、欧氏距离（L2）、内积（IP）

## 第十章 搜索

Milvus 提供四大搜索方式，可灵活搭配满足不同业务场景。

### 10.1 基础相似度搜索

匹配语义最相近的数据，返回指定条数（Top-K）的结果，是最常用的搜索方式。

### 10.2 范围搜索

自定义相似度门槛（距离阈值），所有达标的数据全部返回，不再限制固定条数。适合“找所有高度相似项”的场景。

### 10.3 混合搜索（Hybrid Search）

结合向量相似度 + 标量字段条件过滤，是 RAG 知识库最核心的能力。

python

```
# 示例：语义搜索 + 标量过滤
results = collection.search(
    data=[query_vectors],
    anns_field="embedding",
    param={"metric_type": "COSINE", "params": {"ef": 64}},
    limit=10,
    expr='category == "AI" and status == "published"',  # 标量过滤
    output_fields=["title", "content", "category"]
)
```



**多路融合 + Rerank：**

Milvus 2.4+ 支持同时进行稠密向量搜索和稀疏向量搜索（BM25/SPLADE），然后通过 Rerank 策略融合结果：

- **RRF（Reciprocal Rank Fusion）**：按排名加权融合，无需原始分数可比
- **WeightedRanker**：按预设权重直接加权求和

RAG 最佳实践：先用 RRF 融合语义搜索 + BM25 搜索，再叠加标量过滤。

### 10.4 全文检索（Full-Text Search）

基于关键词的精准匹配（BM25 算法），弥补语义搜索在识别专业术语、缩写、精确名称时的短板。

### 10.5 高级搜索功能

| 功能             | 说明                           | 适用场景                           |
| :--------------- | :----------------------------- | :--------------------------------- |
| **分页查询**     | Offset + Limit 分页            | 搜索结果展示                       |
| **分组搜索**     | 按标量字段分组，组内取最优     | 数据去重，如每个文档只返回一个段落 |
| **迭代搜索**     | 先粗筛后精排，流式返回         | 超大批量数据场景                   |
| **指定返回字段** | 除了ID和分数，直接带出标量属性 | 减少回表查询                       |

### 10.6 搜索参数动态调节

- **nprobe（IVF）**：控制搜索的聚类数量，越大精度越高、速度越慢
- **ef（HNSW）**：控制图搜索的广度，越大精度越高、速度越慢
- 可在每次查询时动态指定，无需重建索引，灵活平衡速度与精度

## 第十一章 存储优化

存储优化的核心目标是在数据库性能和存储成本之间找到最佳平衡点，主要依靠四大机制。

### 11.1 内存映射存储（MMap）

- **原理**：直接把磁盘数据映射到虚拟内存中，依靠操作系统按需加载热点数据
- **价值**：突破物理内存上限，轻松支撑超大规模数据集
- **限制**：仅支持 64 位操作系统

### 11.2 数据聚类压缩

- **原理**：创建集合时指定某个标量字段作为聚类依据，系统将相似数据排序重组、集中存放后统一压缩
- **双重收益**：提升数据压缩比例 + 大幅提高条件过滤的查询速度
- **实测效果**：按高频过滤字段（如 user_id）聚类，查询性能可提升 3-10 倍

### 11.3 强制数据合并（Compaction）

- **背景**：日常写入会产生大量零散的数据碎片（小 Segment）
- **机制**：后台自动将细小数据段合并为完整的大数据段
- **操作**：可手动触发，也可配置自动执行策略
- **效果**：减少碎片、降低读写延迟、释放已删除数据的存储空间

### 11.4 冷热分层存储

- **机制**：系统根据数据访问频率，自动区分热数据和冷数据
  - **热数据**：高频访问，存放于高性能固态硬盘（SSD）
  - **冷数据**：低频访问，自动下沉到机械硬盘或对象存储
- **搭配 TTL**：数据生命周期功能，自动下沉长期未访问的数据
- **回温机制**：冷数据被查询时自动加载回本地缓存

### 11.5 配置灵活性

以上四项优化功能均可针对单个集合独立配置，可结合不同集合的数据特点灵活搭配优化策略。
